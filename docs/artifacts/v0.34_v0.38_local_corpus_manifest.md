# Local corpus manifest — v0.34..v0.38 reducers

**Status:** living doc, additive per-version. Last extended 2026-05-06
(through v0.38). Not a pre-reg; not a contract. A regeneration cookbook
for `runs/` so a session that picks up cold can rebuild the on-disk
corpus the post-hoc reducers consume.

`runs/` is gitignored. Every reducer in v0.34..v0.38 reads sidecars
(`agent_lifetimes.csv`, `config.json`, `manifest.json`) and per-arm
`comparison.csv` written by the underlying sweep drivers. None of those
files are tracked in git. A clean clone has zero corpus on disk and
must regenerate before any reducer can run.

## What "the v0.34..v0.38 corpus" means

96 runs at the locked parameters used by every reducer in the lineage
arc:

- chamber: `tight_gradient`
- influx: `1.0`
- hazard ∈ {0, 4, 8, 12}
- 24 seeds per hazard (v0.25 1..8 + v0.32 9..16 + v0.33 17..24)
- N_TICKS = 200
- N_FOUNDERS = 5

Total: 4 hazards × 24 seeds = **96 runs**. v0.34 onwards reduces this
exact corpus.

## Sweep regeneration commands (in order)

```
uv run python scripts/v0.25_sweep.py    # ~60s; seeds 1..8; both chambers
uv run python scripts/v0.32_sweep.py    # ~13s; seeds 9..16; tight_gradient only
uv run python scripts/v0.33_sweep.py    # ~13s; seeds 17..24; tight_gradient only
```

Total wall time: ~85s. v0.32 + v0.33 are independent of each other and
can be run in parallel if desired (they write to disjoint
`runs/fear-hunger-v0.NN-tight_gradient/` directories).

`scripts/v0.25_sweep.py` writes both `tight_gradient` AND `food_ladder`
output trees; the `food_ladder` tree is unused by v0.34..v0.38 reducers
(they filter to `tight_gradient` only) but the script writes both for
historical compatibility with the v0.25 pre-reg.

Output trees:

- `runs/fear-hunger-v0.25-tight_gradient/` (used)
- `runs/fear-hunger-v0.25-food_ladder/` (NOT used by lineage reducers)
- `runs/fear-hunger-v0.32-tight_gradient/` (used)
- `runs/fear-hunger-v0.33-tight_gradient/` (used)

## Reducer commands (in order; each <5s on the 96-run corpus)

```
uv run python scripts/lineage_replay.py            # v0.34 -> runs/lineage-v0.34/
uv run python scripts/lineage_survival_replay.py   # v0.35 -> runs/lineage-v0.35/
uv run python scripts/trait_replay.py              # v0.36 -> runs/lineage-v0.36/
uv run python scripts/lock_in_timing_replay.py     # v0.37 -> runs/lineage-v0.37/
uv run python scripts/leader_advantage_replay.py   # v0.38 -> runs/lineage-v0.38/
```

Strict ordering required by the re-anchor stack:

- v0.35 reducer reads v0.34's `run_summary.csv` (anchor halts on drift).
- v0.36 reducer reads v0.34's `run_summary.csv`.
- v0.37 reducer reads v0.34's `run_summary.csv` AND v0.35's
  `pre_post_dominance.csv`.
- v0.38 reducer reads v0.34's `run_summary.csv` AND v0.35's
  `pre_post_dominance.csv` (two columns: `leader_lineage_id_at_tick_50`
  AND `eventual_top_lineage_id`).

If any prior reducer's output is missing, the dependent reducer halts
loudly with a `LineageReplayError`.

## Locked anchor invariants (re-asserted at every reducer entry)

- `B_POOL_ANCHORS = {4: 312, 8: 321, 12: 312}` — total
  `births_after_tick_50` across the 24 seeds at each hazard, on the
  v0.34 reducer's `top_lineage_b50` view. Exact (not approximate). A
  drift here means the underlying sweep produced a different corpus.
- `EXPECTED_FOUNDERS = 5` per run.
- `HAZARDS = (0, 4, 8, 12)` (tuple order matters for monotone checks).
- `EXPECTED_N_TICKS = 200` (v0.37 / v0.38 re-assert this from each
  run's manifest.json).

## v0.39 extension (when added)

v0.39 will add a fresh seed stream (25..32, n=8 per hazard at the same
chamber / influx / hazard parameters) via `scripts/v0.39_sweep.py`,
then re-run v0.34 + v0.35 reducers over the combined corpus to extend
their per-run anchor coverage to the new seeds. The v0.39 reducer
(`scripts/leader_advantage_fresh_replay.py`, name TBD) will anchor

After v0.39 lands, the corpus this manifest documents will be 128

```
# (then re-run lineage_replay + lineage_survival_replay over combined corpus)
```

This section will be updated in the v0.39 PR.

## Operational notes

- All reducer outputs are pure functions of the on-disk sidecars +
  per-arm `comparison.csv`. Re-running a reducer over the same corpus
  is idempotent (modulo the unordered `discover_runs` traversal, which
  is sorted internally).
- A failed re-anchor is **always** the right behaviour. If
  `LineageReplayError` fires on a re-anchor, the corpus has drifted
  (different seed, different sweep, different chamber) and the
  reducer's output cannot be trusted. Investigate; do NOT bypass the
  halt.
- Wall-time budget for full regen + all reducers: ~85s sweeps + ~15s
  reducers ≈ **100s**. Acceptable for a fresh-checkout session.
